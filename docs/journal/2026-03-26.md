# 2026-03-26 Weather Screen 아키텍처 리뷰 및 리팩토링

## 배경
AI(오픈클로)가 생성한 Weather 화면 코드를 코드리뷰하면서 아키텍처 문제를 식별하고 개선했다.
동작은 했지만, Clean Architecture 원칙 위반과 구조적 개선점이 다수 존재했다.

## 수행한 작업

### 1. UI 상태 모델 관심사 분리
- `LocationWeatherData`에서 위치 정보를 `LocationInfo`로 분리
- 위치(어디)와 날씨(무엇)의 관심사를 명확히 나눔
- UI 전용 상태 클래스임을 명시하기 위해 `Ui` 접두사 컨벤션 적용
  - `LocationInfo` -> `UiLocationInfo`, `WeatherScreenState` -> `UiWeatherScreenState` 등

### 2. UseCase 간 순환 의존 위험 제거
- `ObserveWeatherUseCase`가 `FetchWeatherUseCase`를 주입받아 호출하는 구조 발견
- 같은 레이어(UseCase) 간 의존은 순환 위험을 내포 (A -> B -> C -> A)
- `CombinedWeatherRepository`를 직접 사용하도록 수정하여 UseCase 간 의존 제거

### 3. 위치 로딩과 날씨 로딩 분리 (프로그레시브 로딩)
- 기존: `ObserveWeatherUseCase`가 위치 목록 + 전체 날씨를 하나의 Flow로 번들링
  - 모든 날씨가 로드될 때까지 UI가 비어있음
- 개선: 위치 목록과 날씨 로딩을 분리
  - `GetLocationListUseCase` 신설 (위치 목록만 Flow로 제공)
  - `LocationItem` 도메인 모델 추가 (날씨 없는 순수 위치 정보)
  - ViewModel에서 위치 먼저 표시 -> 날씨를 위치별로 병렬 fetch
  - `ObserveWeatherUseCase` 삭제

## 아키텍처 판단 기록

### UI 상태에 도메인 모델을 직접 쓰지 않는 이유
- 도메인 모델을 UI 상태에 그대로 담으면 도메인과의 결합이 생김
- 화면에 보여줄 때 가공이 필요한 경우가 대부분이라 처음부터 UI 전용으로 정의하는 게 나음

### UseCase 간 의존을 금지하는 이유
- 같은 레이어끼리 상호 호출하게 실수할 여지가 생김
- 의존 체인이 깊어지면 리팩토링 시 순환이 발생할 수 있고, 컴파일 타임에 잡히지 않음
- 공통 로직이 필요하면 Repository 레이어에서 해결

### Ui 접두사를 선택한 이유
- 코드 읽을 때 패키지까지 확인하지 않으므로, 클래스명만으로 UI/도메인 구분이 필요
- 도메인에는 `Ui` 접두사가 붙을 일이 없으므로 충돌 방지에 효과적
- 접미사(`LocationInfoUi`)보다 접두사(`UiLocationInfo`)가 읽기 자연스러움

## 이력서 활용 포인트

> **AI 생성 코드 아키텍처 리뷰 및 리팩토링**
> - AI 코드 생성 도구를 활용한 빠른 프로토타이핑 후, Clean Architecture 원칙에 맞는 코드 리뷰 프로세스를 주도
> - UseCase 간 순환 의존 위험 식별 및 레이어 의존 방향 정립으로 유지보수성 개선
> - 위치/날씨 데이터 로딩을 분리하여 프로그레시브 로딩 아키텍처로 전환, 체감 로딩 속도 개선
> - UI 상태 모델과 도메인 모델 간 결합도를 낮추는 네이밍 컨벤션 및 관심사 분리 적용

핵심 메시지: "AI를 도구로 활용하되, 아키텍처 판단과 품질 책임은 내가 졌다"

## 회고

코드와 동작 흐름을 함께 보면서 구조적 문제를 식별하고, 설계 방향을 지시해서 리팩토링을 완료했다.
AI가 생성한 코드를 그대로 쓰면 동작은 하지만 아키텍처 원칙 위반이 쌓인다.
코드를 읽고 동작을 이해한 뒤, 어떻게 고쳐야 하는지 설계를 판단하고 방향을 잡는 것 — 그게 시니어의 진짜 가치다.
